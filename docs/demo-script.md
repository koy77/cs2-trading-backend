# demo-script.md — сценарий показа на техническом интервью (~10 минут)

Цель: за 10 минут пройти 5 сцен так, чтобы основные вопросы отпали сами.
Перед встречей: `make demo` (поднимает стек, свежие данные, открывает панель на http://localhost:18090).

Окна, которые держим открытыми: **панель**, **RabbitMQ UI** (http://localhost:25674, cs2/secret),
опционально **Grafana** (`make monitoring-up` → http://localhost:13001), **терминал** (make-команды).

---

## Сцена 0 — что это (30 сек, без кликов)

> «Это демо backend'а трейдинговой платформы CS2 на Laravel: Steam-боковая интеграция **без единого
> API-ключа** — вход через Steam OpenID, публичный инвентарь, цены Steam Market. Дальше классика:
> листинги, покупки, escrow, платежи через PSP с HMAC-вебхуками, выплаты продавцу. Всё на MySQL,
> Redis и RabbitMQ, в Docker, с зелёными PHPStan L8 / PSR-12 / тестами.»

Если спросят «а почему без ключей?» — см. `spec.md` §«Steam без ключей» и README-таблицу.

## Сцена 1 — Steam: вход и инвентарь (2 мин)

1. Панель → **войти как kyle** (демо-вход; отделка: кнопка «Войти через Steam» — это реальный
   OpenID-редирект, показываем, что флоу живой, назад).
2. Нажать **«Синк: live»** → в журнале «задача в очереди inventory.sync». Через пару секунд инвентарь
   прогрузится (79 предметов реального публичного профиля).
   - Говорим: «синк — через очередь, воркер; запросы к Steam идут через общий Redis-троттл-гейт ~1 rps;
     лимиты/429 → ретраи с backoff, режим fixture — слепки реальных профилей».
3. Клик по предмету → **«Продать»** → подставится рыночная цена из Steam Market (кэш Redis, TTL 180с).
4. Если Steam притормаживает/капризничает — кнопка **«Синк: fixture»** (то же, без сети; в CI/тестах
   всегда fixture). «Вот поэтому демо запускается у любого, без ключей и Steam-аккаунта».

## Сцена 2 — Гонка за листинг (2.5 мин) ← главная

1. Нажать **«⚡ Гонка ×30 за листинг»** (панель `demo:race`): 30 отдельных PHP-процессов одновременно
   покупают один и тот же листинг.
2. Итог: **ровно 1 успех, 29 конфликтов (409)**, инвариант «не продать дважды» удержан.
3. Говорим про три слоя: atomic claim (`UPDATE ... WHERE status='active'`, проверка affected rows) →
   unique-индекс на активный заказ (виртуальная колонка) → всё в одной транзакции с проводками.
4. «То же в тестах: `make test-race` — `RaceTest` поднимает процессы и проверяет одного победителя
   и ровно одно списание». (Можно показать вывод.)

Если спросят «а если два сервера?» — «слои в БД, не в приложении: claim и unique-индекс работают
на любом числе инстансов; Redis-локи — только для оптимизаций, не для корректности».

## Сцена 3 — Вебхуки PSP: подпись и идемпотентность (1.5 мин)

1. **«dup ×10»**: один и тот же `event_id` десять раз → ответы 200, баланс изменится **один раз**
   (в журнале: обработано 1, дублей 9).
2. **«bad_sig»** → 401, **«stale»** → 401. Говорим: HMAC-SHA256 по raw body + окно timestamp
   (защита от replay) + unique(provider, event_id).
3. **«Пополнить $10»** — реальный charge к mock-PSP с колбэком обратно в наш вебхук; баланс обновился.
   Кнопки **timeout / http_500** — режимы PSP: таймаут не кредитит (ждём), 5xx — ретраим.

## Сцена 4 — Очереди, сделка, деньги (2 мин)

1. **«Отравить ×5»** → в RabbitMQ UI видно ретраи, затем `failed_jobs`; **«Разобрать failed»** —
   `queue:retry` возвращает в работу. Говорим про backoff, DLQ-подход, идемпотентных консьюмеров.
2. Продавец (войти kyle при необходимости) → **«Принять»** по заказу: escrow → продавцу, комиссия
   платформе (в A/B: 3% или 4% — Pennant, видно в `make report`). **«Отклонить»/«Протух»** — возврат
   покупателю и листинг обратно в продажу.
3. `make ledger-check` в терминале: двойная запись сходится.

## Сцена 5 — Инженерия (1.5 мин)

- `make stan` / `make phpcs` / `make test` — печатаем зелёное (PHPStan level 8, 28 тестов).
- `make explain` + `make perf` — показываем «до/после индекса» на 100k строк (сид — секунды, батчами).
- Раздел AI-воркфлоу: `CLAUDE.md`, `.claude/commands` (feature/review/sync), хук авто-Pint,
  `.mcp.json`, AI-ревью PR в CI (`docs/ai-workflow.md`).
- Grafana (если подняли): заказы по статусам, GMV/комиссии, глубины очередей.

## Частые вопросы и где ответ

Полный список (12) с развёрнутыми ответами — **`spec.md`, Приложение D**. Быстрые отсылки:

- «Где гонки?» → Сцена 2 + `app/Services/Trading/OrderService.php:44` (claim) + `RaceTest`.
- «Идемпотентность вебхуков?» → Сцена 3 + `PspWebhookService` + `WebhookTest`.
- «Почему RabbitMQ, а не database-очередь?» → приоритеты/backoff/DLQ/независимость от БД;
  честно: для простого достаточно database-очереди.
- «N+1?» → сценарии с `with(...)`, `make explain`; в `PanelController` осознанные лимиты выборок.
- «Лимиты Steam?» → троттл-гейт, backoff, кэш TTL, fixture-режим, CI без сети.
- «Секреты?» → только `.env` (`config/`), в коде нет; в CI — сервисные значения.
- «Почему трейд-офферы фейковые?» → у Steam нет официального API создания офферов (сессия+Guard);
  интерфейс `TradeProvider` готов к реальному провайдеру. Это осознанная граница.

## Если что-то пошло не так

| Симптом | Действие |
|---|---|
| Steam 429/таймаут | переключиться на «Синк: fixture», сказать про лимиты |
| Портовые конфликты | `make down`, поправить порты в `.env` (APP_PORT и др.) |
| Панель без данных | `make fresh` (идемпотентный сид) |
| mock-PSP лежит | `make up` (перезапуск), проверить статус-чип «psp» в шапке панели |
| Совсем аварийно | `make demo` — поднимет и пересеет всё с нуля |
